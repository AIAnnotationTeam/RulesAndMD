# 平台能力选择原则

## 适用范围

本文件用于采用本仓库方案设计规范，或明确启用“平台能力清单优先”策略的项目。各端架构和库清单共同引用本文件，平台选型、接入边界及例外条件在此统一维护。

`all-base-最佳实践.md` 与 `all-base-设计模式.md` 独立提供通用工程与设计原则；单独使用这两个文件，不自动启用本文件的平台偏好，也不要求采用本仓库的具体架构模板。

## 外部平台能力选型（强制）

方案设计前必须读取 [Cloudflare 能力清单](../平台能力/Cloudflare能力清单.md) 和 [百炼能力清单](../平台能力/百炼平台能力清单.md) 中与需求相关的条目。外部服务满足需求时优先采用清单方案；UI、网络、本地数据库、系统安全存储和测试库继续遵守各技术栈规范，不作为云平台替换对象。

| 规则 | 执行要求 |
| --- | --- |
| 先能力后 SDK | 先确定业务能力、目标终端、服务平台和运行环境，再确定接入库；库清单中的供应商 SDK 不构成无条件的平台绑定 |
| 优先级 | 用户明确要求和已确认的项目约束优先；新选外部服务先查平台清单，在满足需求的方案中优先采用清单能力；已有项目先评估复用与迁移成本，不因模板更新自动迁移 |
| 适用性验证 | 核对功能覆盖、目标地区、账号资格、测试状态、协议、运行时、配额与成本；清单收录不代表账户已开通或无需验证 |
| 清单缺口 | 清单无完整适用能力时，在方案中写明缺口、保留职责及清单外选型依据，不静默引入其他平台，不为使用清单而自建一套不必要的替代系统 |
| 方案必须确定 | 调研阶段比较候选；提交实施方案时确定每项职责的主实现，列明按业务启用的扩展，不把候选同时装入基线 |
| 选型可追溯 | 架构文档必须记录“业务能力、清单文件及条目、采用方案、验证结论、SDK 与归属”；例外说明无法采用清单能力的原因 |
| 依赖同步 | 架构模板、库清单、目录示例、初始化代码与依赖声明必须一致；使用外部服务才引入对应 SDK |
| 服务端边界 | 云管理令牌、模型长期 API Key、支付私钥和数据库管理凭据只保存在可信服务端；客户端只持有公开配置、用户会话及受限短期凭证 |

| 业务能力 | 清单优先路线 | 必须保留的边界 |
| --- | --- | --- |
| 产品账号 | Workers + D1 + Better Auth，事务邮件采用 Email Sending | Better Auth 是第三方框架；核对所需登录方式、会话和移动端接入；已有认证不自动迁移 |
| 受控入口 | Access + 适用登录方式与策略 | 不直接代替产品资源授权，Cloudflare 账号 OAuth 不等于任意用户账号系统 |
| 云端数据库 | 优先评估 D1；房间协调采用 DO | 按事务、同步和数据模型验证；D1 不等同 PostgreSQL / RLS，也不替代本地数据库 |
| 文件与后端 | R2、Workers；系统工具和完整进程使用 Containers | 客户端经后端 API / 签名访问；Callable、数据库事件和离线同步需重新适配 |
| AI 能力 | 从百炼清单按视觉、生成、ASR、TTS、实时对话、同传和检索分别选型；Cloudflare Workers AI 按其清单适用性评估 | 具体模型与协议由项目确定；不把 OpenAI 专用客户端当成百炼兼容客户端 |
| 实时音视频 | Realtime SFU + 按需 TURN / 媒体适配器 | 与信令、房间状态、AI 翻译职责分离；格式、延迟和容量需联调 |
| 服务端监控与统计 | Issues、Logs、Traces、Alerts；自定义指标采用 Analytics Engine，事件分发按需用 Zaraz | 不替代移动原生崩溃、ANR、符号解析或完整广告归因；采样统计不作支付账本 |
| 通知 | 浏览器 / PWA 评估 Web Push，事务邮件评估 Email Sending | 原生系统推送继续接 APNs、FCM 或厂商通道；本地通知不改成云端通知 |
| 支付 | 国内普通业务优先支付宝，海外评估 Stripe；按平台清单支付场景表确定 | 两者为外部集成；商店内购与必要订阅管理保留，机器付费协议不能直接替代普通支付 |

新项目不再默认绑定 Firebase 云端认证、Firestore、Storage、Functions、Supabase 全套服务或 OpenAI Realtime。只有记录明确需求与选型依据后才采用；Firebase 原生推送、Crashlytics 等未被清单完整覆盖的客户端职责不受此条禁用。


### 客户端接入边界

以下规则统一维护，各端文档只补充技术栈差异；平台能力、套餐与账号条件以对应能力清单为准。

| 能力 | 统一接入要求 |
| --- | --- |
| 账号与数据 | 原生认证须验证回调、会话刷新和退出；通过项目 API 访问云端数据，不从客户端直连 D1；Firestore 离线同步与 PostgreSQL/RLS 语义须独立评估 |
| 模型与媒体 | 服务端适配模型协议与长期凭据，客户端保留采集、播放和必要 WebRTC 库；SFU 仅转发媒体，翻译链路须验证格式、时延和译音回传 |
| 监控与事件 | Workers 优先评估 Issues / Workers Traces，其他运行环境按覆盖情况选型；客户端继续承担原生崩溃、ANR、符号化与性能诊断。Zaraz 不作为原生 SDK，HTTP 事件端点须校验授权、防滥用并最小化数据 |
| 通知与邮件 | Web Push 面向浏览器，不替代 APNs、FCM、厂商推送或本地通知；Email Routing 不替代主动发信，Email Sending 须核对域名、账号资格与收件范围 |
| 支付 | 普通 Web 收款国内优先支付宝，海外评估 Stripe；两者为外部集成。商店内数字商品和订阅按发行渠道规则接入，机器支付不作为普通用户默认收银台 |
| 凭据 | 云管理、模型及支付长期密钥留在可信服务端；客户端直传与媒体接入只在已验证场景使用受限短期凭证，用户会话按平台安全存储规范管理 |

## 平台 SDK 适配

平台 SDK 通过适配器隔离，业务层依赖能力契约。先按清单验证并确定实际方案，再创建该方案所需实现；不为尚未启用的平台预装 SDK。不同云数据库、认证和模型协议需要分别实现适配，不能只替换地址就认定兼容。

## 支付通道适配示例

**在一个项目中，如果一个功能存在多种实现类型，不同的类型支持像插件一样互相替换，而不影响其他逻辑流程，典型例子：不同的支付通道（普通 Web 收款国内优先支付宝，海外评估 Stripe；商店内数字商品和订阅按渠道规则采用 StoreKit / Google Play Billing，可按需使用 RevenueCat）通过统一契约接入。各通道的下单、回调、退款和权益校验保留自身语义。**

1. 定义一个PayAdaptor 抽象父类，里面定义了支付所使用的接口和属性
2. 仅为已选通道定义实现，例如 AliPayAdaptor 或 StripePayAdaptor；商店内购另设平台适配。根据官方文档实现接入，签名、回调验签和可信权益校验在服务端完成
3. 在业务流程中，跟发布场景，动态使用不同的 PayAdaptor子类
